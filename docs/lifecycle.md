# Agent lifecycle deadlines

Every subagent has one finite lifecycle policy accepted at initial delegation and stored before worker/provider startup. Every configured delay must be an integer from 1 through `2147483647` milliseconds, the maximum Node can represent safely with `setTimeout`; larger values are rejected or ignored. Multi-phase cleanup durations use chunked absolute deadlines, so `abortTimeoutMs + disposeTimeoutMs` preserves its full semantics without ever passing an overflowing delay to Node. The policy is copied into the durable first-mail spawn intent alongside exact provider/model binding and effort, so recovery from a crash between mail acceptance and registry persistence reconstructs the same values without selecting a provider again.

## Semantics

- `spawnTimeoutMs`: one absolute deadline covering worker factory creation and `start`.
- `promptAcceptanceTimeoutMs`: bounds prompt preflight/acceptance and immediate steering delivery.
- `runTimeoutMs`: absolute maximum for each accepted worker run, including mailbox-enforcement runs. Model activity and active tools never extend it.
- `idleTimeoutMs`: stall deadline during an active run when no tool call is known to be in flight. Worker activity resets it. A tool start disarms only the idle timer; after the last exact parallel tool-call ID ends, a fresh idle interval starts. A worker resting normally in the `idle` state has no active idle/stall timer.
- `abortTimeoutMs` and `disposeTimeoutMs`: caller-response deadlines inside one idempotent worker cleanup operation. Expiry records a timeout but does not cancel or forget the underlying cleanup.
- `brokerShutdownTimeoutMs`: global broker deadline. It is administrator-configured and rejected in an initial delegation override.

Run and idle timers start fresh after prompt acceptance and are removed on settlement, failure, stop, archive, restart, and shutdown. Pi-managed provider retry/backoff remains inside that one accepted run and does not reset the absolute deadline. Retry start/end is ordinary bounded activity and can refresh only the idle-stall observation; Pi alone owns its continuation. Tool calls that start immediately before watchdog installation are retained for that exact worker/run generation. Parallel calls are tracked by stable call ID, so duplicate or orphan boundaries cannot arm idle early. Only content-free start/end boundaries are forwarded to the broker; arguments, commands, progress, partial results, stdout, and stderr are not forwarded or persisted.

Restart creates fresh timers while preserving the identity's exact persisted provider/model. A timed-out factory first installs a generation-specific pending-factory quarantine. Explicit restart cannot allocate generation G+1 until factory G settles and any exact late worker is cleaned; a stale late callback cannot release a newer slot/watchdog/epoch. A stopped or archived identity never follows a later main-provider preference; an absent exact tuple makes restart unavailable rather than substituting another provider. A timeout detaches the old worker from routing immediately and records the stable `LIFECYCLE_*_TIMEOUT` failure, but does not release ownership merely because a bounded wait ended. One cleanup lease owns abort, disposal, late settlement, and the exact worker generation. Settlement continuations are also worker/generation-owned; management invalidates and joins the old continuation before replacement. While cleanup is pending or unknown, its exact inherited run slot (if any) and activation capacity remain held, restart/archive/clear-failure are blocked, and newly accepted mail stays queued under a materialized recipient record. The last verified release resumes those queued admissions. If a caller-visible restart times out, a late verified release leaves the identity paused; only a new explicit restart creates a replacement.

An unknown cleanup for a generation that was mutation-capable at start also blocks new mutable prompt, steer, schedule, and enforcement admission in this parent broker. Admission uses a quarantine epoch rechecked after journal awaits and at the synchronous prompt/steer boundary. Already-running siblings are not retroactively isolated. This is containment within one broker keyed by one parent session; it is not project-wide or cross-parent workspace isolation, and another parent broker sharing the same working directory is outside this quarantine.

Only a structured `quiescence: verified` worker report releases an in-memory quarantine. `SdkWorker.cleanup()` remains one pending operation until the real Pi abort settles; broker deadlines bound callers without cancelling that operation. Pi 0.81.1 documents `AgentSession.abort()` as waiting for session idle, but exposes no public built-in-tool/process-group absence receipt. The compatibility gate `processQuiescenceReceiptCapability()` is therefore disabled for this release; a similarly named method on an untested host cannot enable it. Integration requires a released, deliberately version-tested, idempotent session/generation receipt covering provider and callback settlement plus active and completed process-tree receipts. This extension retains generation-level process risk once built-in Bash starts: cleanup stays `unknown` even if Bash already returned successfully, the active-tool map is empty, SDK abort returns, and session disposal succeeds. Clean SDK cleanup can verify session/provider callback settlement only when no process-capable tool ran in that generation.

Distinguish **live cleanup pending**, whose exact in-memory cleanup lease still has an owner and may settle late, from **persisted/process-risk unknown**, whose Promise owner or authoritative receipt is unavailable. Waiting cannot manufacture proof for the latter, and there is no automatic waiting period, quarantine expiry, capacity release, namespace release, restart, or archive. A future supported receipt may strengthen this only for its exact matching generation and tested platform/topology.

A directly recorded Linux E2E case observes that one ordinary same-process-group Node parent and descendant launched by built-in Bash are both absent and its heartbeat stops after abort. A second case observes Bash returning success while a redirected background heartbeat survives; stop and restart remain quarantined rather than overlapping it. These observations do not supply the missing generic receipt. Deliberately escaped POSIX sessions/groups, other process topologies, and the historical surviving `worker.js` topology remain unverified. No Windows process-containment claim is made without a released Pi-owned equivalent such as a tested Job Object receipt.

Persisted cleanup state contains only bounded phases, confidence, tool IDs/names, timestamps, the exact generation's `mutationCapableAtStart` fact, and whether that cleanup inherited a `heldRunSlot`. A process restart converts `pending` to sticky `unknown` because the Promise owner was lost; current configuration cannot overwrite the old capability, and lower limits preserve inherited cleanup overcommit without inventing ordinary leases. A known active tool remains bounded by the finite absolute run deadline. For Bash work that needs a smaller tool-specific bound, pass Bash's `timeout` argument; it can expire before `runTimeoutMs` without changing lifecycle policy.

The namespace lock is a cooperative per-parent state lease only within the same local host and PID namespace, not a workspace, distributed-filesystem, container-boundary, or security fence. On Linux, owner metadata records the boot ID and `/proc/<pid>/stat` start time. A stale mtime is never enough to take the lease from an exact live or `SIGSTOP`ed process. Missing/stale/dead sidecars and lock directories remain fail-closed orphans because lock acquisition, owner publication, and release cannot be atomically generation-bound through Pi's public surface. Manual recovery and orphan removal require independently verified local-host/PID-namespace quiescence; waiting or elapsed stale time never authorizes takeover. The broker does not restore or admit mail while the orphan lease exists. After deliberate manual recovery, existing durable cleanup diagnostics remain authoritative and any persisted `unknown` quarantine still blocks restart/archive and preserves queued mail. Platforms without the required kernel identity fence likewise fail closed rather than falling back to mtime-only recovery.

Broker shutdown returns within the global bound even when cleanup hangs, but namespace ownership is released only after worker/session cleanup, in-flight mutation barriers, persistence, flushes, and cleanup leases are known quiescent. If any operation times out, rejects without proof, or remains persisted unknown, shutdown fails promptly while deliberately retaining the namespace lease. Session replacement refuses to initialize a new broker after such a failed handoff. `brokerShutdownTimeoutMs` is global administrator-only configuration and is not part of the six-field delegation schema.

## Resolution and mutation

Each field resolves independently:

1. Initial `send_email.lifecycle` for an unknown recipient.
2. `addresses[canonicalAddress].lifecycle`.
3. `roles[name].lifecycle`.
4. Global `lifecycle` defaults.

Every requested field must be a positive integer no greater than its `lifecycleMaxima` field. Later mail cannot mutate a live, stopped, failed, or archived identity. Archived restoration deliberately preserves the original policy; a future explicit management action would be required for safe mutation.
